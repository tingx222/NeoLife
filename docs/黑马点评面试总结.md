## 登录：可讲清楚的请求链路

验证码写Redis String并设短TTL → 校验 → 查找或创建用户 → 随机Token → Redis Hash保存UserDTO → authorization请求头 → RefreshTokenInterceptor恢复用户到ThreadLocal并续期 → LoginInterceptor校验登录 → afterCompletion清理ThreadLocal。

Redis共享登录态解决多实例共享；ThreadLocal只保存当前请求线程上下文，必须清理防止线程复用串号。随机令牌不是JWT，不要混称。当前成功登录后没有删除验证码，可在有效期复用；建议原子校验消费、发送限流、注册并发约束。退出应删除Token Key。正式环境不能打印验证码。

## 缓存：穿透、击穿、雪崩

穿透是查不存在的数据，空值缓存短TTL减少重复回源；布隆过滤器可进一步过滤，但本项目没实现。击穿是热点Key失效，大量请求同时回源；逻辑过期先返回旧值并异步重建，以实时性换可用性。雪崩是大量Key同时过期或Redis不可用，可用随机TTL、限流降级与高可用应对，当前没有完整实现。

实际缺口：queryWithLogicalExpire缓存缺失直接return null；ShopServiceImpl.update删除缓存后可能把真实商户显示为不存在。修复方向是冷缓存查询DB并按逻辑过期结构写回，或可靠预热与刷新。普通JSON与RedisData结构不能直接混用。

CacheClient double-check发现数据已刷新时直接return，已获得的锁没有释放，只能等待TTL。其锁value固定为1，直接delete不核验持有者，锁过期后可能删别人的新锁；应使用所有者校验Lua或Redisson。无界线程池队列也需要容量和关闭管理。

先更新数据库再删缓存是Cache Aside。当前删除发生在事务提交前，其他读请求可能回填旧值；DB与Redis并非同一事务。可事务提交后删除，配合重试或消息补偿。这样仍属于最终一致性，不应宣称强一致。

## 秒杀：防超卖不等于防重复订单

现有流程：查活动时间和库存 → 用户粒度Redisson锁 → AopContext代理进入事务方法 → 查用户券订单 → UPDATE stock=stock-1 WHERE voucher_id=? AND stock>0 → Redis ID → 保存订单 → 事务提交 → finally解锁。

条件SQL原子判断库存，防超卖；用户锁保护查重和创建的组合操作；事务保证扣库存和订单一起提交。代理事务返回后再释放锁，避免前一个事务没提交就让下一请求进入。@Transactional自调用绕过代理，本项目启用exposeProxy；更清晰的方案是拆独立事务Bean。

数据库应检查并补齐(user_id,voucher_id)唯一索引兜底；先核验现有索引和历史重复，不能只依赖分布式锁。活动券不存在当前会空指针。全部同步访问数据库，不能称为Redis异步秒杀。

异步方案知识：Lua原子检查活动、库存、一人一单并发Stream消息；消费者事务写DB，成功ACK；处理重复消费、Pending重试、失败补偿和状态查询。Redis入队成功不等于数据库下单成功。这些是后续设计，当前没有实现。

## 锁与ID追问

SET NX EX原子加锁。解锁必须比较持有者再删除，用两个命令存在过期重新加锁的竞态，所以使用Lua。Redisson支持重入、续期等；不指定leaseTime时watchdog续期有助于覆盖慢任务，仍不能替代数据库约束和幂等。

RedisIdWorker把相对起始秒数左移32位，与每日INCR序列做OR。集中分配简单但依赖Redis。当前没有每日计数Key清理、溢出防护和显式统一时区；多实例时区必须一致。测试类雪花算法不是生产订单ID方案。测试大量日志、依赖外部服务，没有可信基准，不能编造QPS或性能提升。

## 未完成模块：可以讲设计，不能说已完成

ZSet点赞：member=userId，score=时间戳，实现状态、取消和排行，跨DB/Redis写要考虑一致性。共同关注：每人Set，SINTER求交，处理DB同步和历史初始化。

Feed：发布时写扩散到粉丝ZSet，按时间戳score滚动分页；同时间戳需offset处理，避免重复遗漏。大V粉丝很多可推拉结合。普通页码在数据持续新增时易移动。

GEO：按类型建Key存坐标，半径查询并按距离排序，批量查询DB后保持距离顺序。Bitmap：按月建Key，日偏移SETBIT，BITFIELD读位串计算连续签到，跨月单独设计。HyperLogLog：近似UV，不能返回具体用户，不能用于精准计费。

## 面试介绍示例

“我实践了Redis登录态、商户缓存、分布式锁和同步秒杀。用数据库条件扣库存防超卖，用用户锁与事务保护一人一单流程。我也检查出了逻辑过期冷缓存和缓存删除时机的问题。后来增加DeepSeek只读客服，通过受控工具查商户和本人订单，后端控制权限与调用次数。”

不宣称生产上线、未经压测的QPS、完整教程全实现、支付退款闭环或向量RAG。建议补齐顺序：冷缓存和事务后删除 → 唯一索引 → 登录退出与限流 → 点赞关注 → 异步秒杀可靠性 → GEO和签到。
