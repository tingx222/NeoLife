## 二、为什么这样实现

### 异步秒杀不是“入队就成功”

用户请求只做Redis资格判断与预扣，返回受理订单号。消费者调用独立的OrderWriter Bean进入数据库事务：检查同一订单是否已落库、检查重复用户券订单、条件扣库存、保存订单。只有这些提交后才ACK，随后删除已处理消息和处理中标记。

数据库提交后ACK失败会重投，但按orderId幂等检查避免再次扣库存。消费失败保留Pending，下一轮优先恢复；已受理订单通过查询接口等待最终落库。前端先提示受理，不能把“队列收到了”描述为“交易成功”。状态SUCCESS表示订单记录已创建，不表示已经支付。

本实现面向本地课程的Redis单机：固定消费者名配合全局Redisson消费锁，避免多个进程同时处理同一消费者身份，并支持重启恢复其Pending。每200毫秒最多处理10条；选择可理解的恢复流程，未宣称高吞吐多消费者集群。Redis Cluster的Lua多Key同槽、分片消费者与claim接管需要另做设计。

活动缓存首次按数据库库存初始化，同时导入已有购买用户；如该券仍有Stream消息而活动缓存丢失，拒绝盲目重置库存，要求人工对账。数据库一人一券唯一索引是最后一道约束。不能在有处理中订单时随意删除活动、购买标记或Stream。

### 点赞、关注与Feed

点赞ZSet member为用户ID，score为点赞时间。SQL计数与Redis状态在笔记粒度锁内更新，支持取消和排行。关注关系以DB为准，Redis Set原子rename替换；共同关注前从DB重建，兼容之前没有Redis集合的历史关系。

发布笔记保存后，将笔记ID写入每个粉丝收件箱ZSet。拉取使用最后时间戳和offset，处理多篇笔记同毫秒发布的情况。只向发布时已有粉丝投递；新关注不会自动补发全部历史笔记。DB与Redis之间没有分布式事务，故障时仍可能出现点赞计数偏差或Feed漏投，生产需Outbox/补偿任务，不能宣称强一致。

### 缓存、GEO、Bitmap和HLL

逻辑过期的数据始终使用RedisData封装，冷加载不会误把真实店铺判为不存在。热缓存过期仍允许返回旧值并异步重建。更新后在事务提交后删缓存，减少提交前回填旧值的窗口；Redis删除失败仍需要生产补偿。

GEO在当前Spring Data Redis版本使用兼容的GEORADIUS调用，效果为半径检索+距离排序。前端默认明确显示杭州示例坐标，点击“使用我的位置”才向浏览器请求定位。签到不做跨月连续计算，与讲义的月度位图规则一致。UV统计的是每日已登录用户，不是所有匿名浏览器；HyperLogLog是近似统计，不可用于精准计费。

## 四、运行与复现

已有数据库不要重新导入`hmdp.sql`，它包含DROP TABLE，会覆盖数据。已有库使用：

```powershell
python scripts/Upgrade-Database.py
```

脚本使用本机mysql客户端，读取application.yaml的数据源或SPRING_DATASOURCE环境变量，临时凭据文件用后清除；如果发现重复关系会停止，不擅自删除。新建空库才使用初始化SQL，本次已为新库增加唯一索引，并替换零日期默认值以兼容严格模式。

确认MySQL和Redis可达；后端配置在application.yaml；图片目录可通过`HMDP_UPLOAD_DIR`覆盖。需要客服时配置DEEPSEEK_API_KEY。先在IDE停止旧8081进程，再运行：

```powershell
mvn spring-boot:run
```

打开 http://localhost:8080/index.html，Ctrl+F5。登录仍为开发验证码方式：手机号发送验证码后从Java日志取码，成功登录会消费验证码。没有真实短信供应商。当前密码登录页不属于讲义验证码登录实现。

前端重复安装（会备份当前文件）：

```powershell
./scripts/Install-CustomerFrontend.ps1
./scripts/Install-LocalNginxConfig.ps1
```

这些脚本会写仓库外的Nginx目录，运行环境可能要求授权。未来需要双实例时，再向upstream添加确实正在运行且连接同一DB/Redis的第二实例。

## 五、验收入口

1. 首页分类、商户详情：未登录可看商户分类和店铺；冷Redis缓存也应显示真实详情。
2. 登录后进入个人页，点击每日签到，再次点击不重复计数；退出后旧token不再可用。

8. 客服仍需有效DeepSeek密钥；真实模型调用没有在本次业务测试中替代验证。
